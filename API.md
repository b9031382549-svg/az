# API классификатора

HTTP API для внешних систем: отправить позиции на классификацию по кодам XİF MN, забрать ответы, следить за состоянием сервиса. Всё в JSON, кроме health-check (простой текст).

Базовый адрес — `http(s)://<host>/api`.

## Доступ

Каждый запрос — с токеном в заголовке:

```
Authorization: Bearer <token>
Accept: application/json
```

Токены выпускают и удаляют в интерфейсе: **Настройки → API-токены**. Токен показывается один раз, сразу после создания. В базе хранится только его хеш, поэтому восстановить токен нельзя — можно выпустить новый.

У токена есть права:

| Право | Что открывает |
|---|---|
| `classify` | `POST /api/classify`, `GET /api/classify/{id}` |
| `results` | `GET /api/results/{item}`, `GET /api/uploads/{batch}` — подробные трассировки решений |

`GET /api/health-check` и `GET /api/version` работают с любым действующим токеном.

| Ответ | Когда |
|---|---|
| `401` `{"message": "Unauthenticated."}` | нет токена или он неверный/удалён |
| `403` `{"message": "Invalid ability provided."}` | у токена нет нужного права |
| `404` | нет такого запроса |
| `422` | тело запроса не прошло проверку (формат ниже) |

## Как устроена классификация

Классификация занимает время: память, правила, модель-сортер, ИИ-механизмы, веб-поиск при расхождении, в конце — проверка людьми. Поэтому API асинхронный:

1. `POST /api/classify` с позициями → сразу `202` и `request_id`.
2. `GET /api/classify/{request_id}` раз в 10–30 секунд, пока `status` не станет `done`.

Один запрос — одна загрузка в системе. Она видна в интерфейсе («Очередь проверки») с подписью `API · <имя токена>` и проходит тот же конвейер, что загрузка файлом.

## POST /api/classify

```json
{
  "items": [
    {"name": "ANSIMAR-400mg-N20-TAB"},
    {"name": "X7 NANO BLACK 4 SIQARET YENI", "unit": "blok", "series": "MT", "number": "1001"}
  ]
}
```

- `items` — от 1 до 100 000 позиций.
- **Обязательно только `name`** — название из накладной, до 5000 символов.
- Остальные поля — по желанию: поля строки накладной (Şablon) под этими именами.

| Поле | Что это | Формат |
|---|---|---|
| `supplier_tax_office`, `supplier_name`, `supplier_tin` | продавец: налоговый орган, название, VÖEN | строка (VÖEN можно числом) |
| `recipient_tax_office`, `recipient_name`, `recipient_tin` | покупатель | строка |
| `invoice_type` | вид е-накладной | строка |
| `invoice_date`, `approval_date` | дата накладной, дата подтверждения | `dd.mm.yyyy` или `yyyy-mm-dd` |
| `series`, `number` | серия и номер накладной | строка |
| `declared_group`, `declared_code` | группа и код, которые указал поставщик | строка |
| `unit` | единица измерения | строка, как в накладной |
| `quantity` | количество | число или `"1 234,5"` |
| `excise_amount`, `vat_taxable_amount`, `non_vat_taxable_amount`, `vat_exempt_amount`, `zero_rated_vat_amount`, `vat_amount`, `road_tax`, `total_amount` | суммы | число или `"1 234,50"` |

Что происходит с полями:
- **В классификатор уходит только название.** Код поставщика и прочие поля на ответ не влияют.
- Строка с полями накладной сохраняется так же, как строка из загруженного файла Şablon. Её видно на странице «Накладные» и в ИИ-чате. Если накладная с той же серией и номером уже загружена раньше, строки второй раз не пишутся, но названия всё равно классифицируются.
- Неизвестные поля молча игнорируются.

**Ответ `202 Accepted`** (и заголовок `Location: /api/classify/<request_id>`):

```json
{
  "request_id": "033efd90-57f2-4c47-a49e-07632c5d218f",
  "status": "accepted",
  "lines": 2,
  "names": 0,
  "answered": 0,
  "created_at": "2026-10-02T09:00:41+00:00",
  "error": null
}
```

**Ответ `422`**, если формат неверный (показываются первые 20 ошибок):

```json
{
  "message": "Every item needs a name. (and 1 more error)",
  "errors": {
    "items.1.name": ["Every item needs a name."],
    "items.4.name": ["A name can be at most 5000 characters."]
  }
}
```

## GET /api/classify/{request_id}

Состояние запроса и ответы по названиям, страницами: `?offset=0&limit=1000`. По умолчанию 1000, максимум 2000.

```json
{
  "request_id": "033efd90-57f2-4c47-a49e-07632c5d218f",
  "status": "processing",
  "lines": 4,
  "names": 4,
  "answered": 3,
  "created_at": "2026-10-02T09:00:41+00:00",
  "error": null,
  "offset": 0,
  "limit": 1000,
  "classified_items": [
    {
      "name": "X7 NANO BLACK 4 SIQARET YENI",
      "category": "2402",
      "similarity": 0.93,
      "kind": "good",
      "units": ["blok"],
      "status": "answered",
      "method": "consensus",
      "reason": "Two independent methods agree: the AI model (Direct) chose 2402, and the catalog vector search ranks it #1 of 3."
    },
    {
      "name": "Hesab-faktura 123",
      "category": null,
      "similarity": 0.98,
      "kind": "trash",
      "units": [],
      "status": "answered",
      "method": "trash",
      "reason": "Only a document reference, date or period — no product is named."
    }
  ]
}
```

### Запрос целиком

| Поле | Значение |
|---|---|
| `status` | `accepted` — принят, ещё не разобран; `processing` — в работе; `done` — автоматика ответила по всем названиям; `failed` — запрос не удалось прочитать (причина в `error`) |
| `lines` | сколько позиций было в запросе |
| `names` | сколько записей в `classified_items` — разных названий |
| `answered` | по скольким из них автоматика уже закончила |

### Одно название

Записи идут по одной на каждое **разное название ровно в том виде, как его прислали**, в порядке первого появления. Одинаковые строки схлопываются в одну запись. Названия, которые отличаются регистром или пробелами, классифицируются один раз, но в ответе каждое написание отдельной записью — сопоставлять можно простым сравнением строк. Нормализация азербайджанская: `I` ↔ `ı`, `İ` ↔ `i`. Поэтому `ANSIMAR` и `ansimar` система считает разными названиями.

| Поле | Значение |
|---|---|
| `name` | название, как прислали |
| `category` | код XİF MN: обычно позиция из 4 знаков (`2402`); `99` — услуга; 10 знаков, если человек при проверке выбрал точный код. `null` — мусор или пока нет ответа |
| `kind` | `good` — товар, `service` — услуга, `trash` — строка, в которой не названо никакого товара (номер документа, дата, ФИО…). `null`, пока нет ответа |
| `units` | единицы измерения, с которыми это название пришло в строках запроса. Пусто, если не присылали |
| `status` | `pending` — ещё классифицируется; `answered` — есть ответ; `needs_review` — автоматика не смогла уверенно решить, решит человек |
| `similarity` | насколько можно доверять ответу (см. ниже). `null`, пока нет ответа |
| `method` | каким способом найден ответ (см. ниже) |
| `reason` | почему такой ответ — коротко, по-английски |

**Ответ может измениться позже.** Позицию со статусом `needs_review` решает человек, и тогда в ней появится ответ. Человек может и исправить уже выданный ответ. Чтобы забрать изменения, запросите `GET` ещё раз.

### similarity

Это **не косинусная близость**, а измеренная доля верных ответов среди найденных тем же способом, на уровне 4-значной позиции. Удобно ставить порог: всё, что ниже, — на ручную проверку у себя.

| `method` | Как найден ответ | `similarity` |
|---|---|---|
| `human` | решение человека | 0.99 |
| `trash` | правила / модель-сортер: в строке нет товара | 0.98 |
| `memory` | в памяти есть проверенный ответ на это название | 0.97 |
| `consensus` | два независимых метода согласны: ИИ-модель (Direct) и векторный поиск по каталогу | 0.93 |
| `web_search` | методы разошлись, позицию уверенно определил веб-поиск, и она есть среди кандидатов наших механизмов | 0.95 |
| `web_search` | то же, но без такой опоры | 0.45 |
| `sorter` | ИИ-модель и модель-сортер согласны, что это услуга | 0.90 |
| `ensemble` | методы разошлись, позицию выбрало повторное голосование по каталогу | 0.70 |
| `ai` | выбрано автоматически, подробности не сохранились | 0.50 |

Пока ответа нет, `method` = `in_progress` (ещё в работе) или `needs_human` (ждёт человека).

Значения `similarity` — это настройка (`config/api.php`). Их пересчитывают по контрольным данным после смены моделей.

## GET /api/health-check

Проверка «всё работает» для мониторинга. Каждый пункт проверяется в момент запроса, быстро и бесплатно: ничего не классифицируется. Ответ — простой текст:

- `200` `Health check passed`
- `500` `Health check failed — workers: no queue workers are running; llm: TokenFactory (fallback, base) does not offer …`

Что проверяется:

| Пункт | Проверка |
|---|---|
| `database` | база отвечает |
| `redis` | очередь отвечает |
| `workers` | воркеры очереди запущены и не на паузе — иначе принятые запросы не обработаются |
| `sorter` | сервис модели-сортера жив |
| `embedder` | в Ollama есть модель эмбеддингов |
| `vector search` | работает поиск ближайших соседей по каталогу |
| `llm` | модели, которые принимают решения, всё ещё есть у своих провайдеров (список моделей кешируется на 5 минут) |

Под большой нагрузкой health-check не краснеет: занятый сервис не считается упавшим.

## GET /api/version

```json
{
  "model_version": "1.0.0",
  "trained_at": "2026-10-01",
  "api_version": "1.0",
  "components": {
    "sorter": "sorter-v1",
    "embedder": "bge-ft-v3",
    "direct": "gpu:tuned",
    "direct_fallback": "deepseek-ai/DeepSeek-V4-Flash-0731",
    "web_search": "deepseek/deepseek-v4-flash:online"
  }
}
```

- `model_version` — версия классификатора целиком. Меняется при смене любой модели, порога, промпта или правила, от которых зависят ответы.
- `trained_at` — дата самой свежей модели, которую обучали мы.
- `components` — модели, на которых цепочка настроена прямо сейчас (читаются из конфигурации). Выключенные части не показываются. `direct` = `gpu:…` означает модель на своём GPU-сервере; пока он не запущен, работает `direct_fallback`.

## Пример

```bash
TOKEN=...   # Настройки → API-токены

curl -s -X POST https://<host>/api/classify \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -H "Accept: application/json" \
  -d '{"items":[{"name":"ANSIMAR-400mg-N20-TAB"},{"name":"X7 NANO BLACK 4 SIQARET YENI","unit":"blok"}]}'
# → {"request_id":"033efd90-…","status":"accepted",…}

curl -s "https://<host>/api/classify/033efd90-…?offset=0&limit=1000" \
  -H "Authorization: Bearer $TOKEN" -H "Accept: application/json"
# повторять, пока "status" не станет "done"; при names > 1000 листать offset
```

## Подробные трассировки (право `results`)

- `GET /api/results/{item}` — одна позиция со всеми шагами решения.
- `GET /api/uploads/{batch}?limit=200&resolution=conflict` — позиции загрузки. `batch` у API-запроса совпадает с `request_id`.
